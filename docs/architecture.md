# Architecture

How LePika works, and why it's built this way. For what it does, read the [README](../README.md).

## The shape of it

LePika is a thin orchestrator. It never reimplements inference, UIs, or package management — it detects the machine, asks a few questions, and drives the real tools:

```
LePika CLI (Python: Typer + Rich, structlog for the log)
 ├─ detect.py   OS / arch / GPU / RAM / what's already installed
 ├─ wizard.py   the default `lepika` experience (≤4 questions)
 ├─ models.py   model refs (3 shapes) + curated list (models.toml)
 ├─ engine.py   the Ollama HTTP API (tags/delete/pull/import, Bearer key) + the vLLM health probe
 ├─ hf.py       the Hugging Face CLI (hf via uv tool run): pre-flight listing, resumable download, token
 ├─ express.py  Express backend: native Ollama + OpenWebUI via uv
 ├─ server.py   Server backend: docker compose (profiles engine · vllm · expose), .env, API key
 ├─ stack/      compose.yml · compose.nvidia.yml · Caddyfile (copied into ~/.lepika/stack)
 ├─ config.py   ~/.lepika/config.toml (flat, versioned, atomic 0600 writes)
 ├─ doctor.py   diagnostics; every ✗ ships a one-line fix
 ├─ proc.py     the single subprocess choke point (logged, friendly)
 ├─ log.py      structlog → JSON lines, secrets redacted
 └─ cli.py      commands: up · down · status · logs · doctor · update · connect · expose · model
State: ~/.lepika/ — config.toml, logs/, *.pid, hf/ (full-weight downloads, deleted after a successful import), openwebui/ in Express, stack/ in Server (override with LEPIKA_HOME)
```

**Express mode** (the default): no Docker anywhere. Ollama runs natively (Homebrew / official script / winget) so the GPU works on every platform — Metal on Mac, CUDA on Windows/Linux — and OpenWebUI runs via `uv tool`. **Server mode** (`lepika --mode server`, or picked in the wizard when Docker is already installed): one docker compose stack — OpenWebUI, an ollama container, a Caddy proxy that gates the engine API on a generated key (`lepika expose`), and a vLLM profile (Linux + NVIDIA) for full-weight Hugging Face repos. `cli._backend(cfg)` picks the module — `express` and `server` expose the same `start_stack`/`stop`/`update`/`logs` surface, so every lifecycle command is written once.

## Design rules

These are load-bearing; changes should preserve them.

1. **Three runtime dependencies** — typer, rich, and structlog (one JSON-lines log at `~/.lepika/logs/lepika.log`). Stdlib for everything else (urllib, tomllib, ctypes, socket, json, secrets).
2. **Every user-reachable failure is a `FriendlyError(problem, fix)`** — one red line, one suggested next step, never a traceback. `proc.run_logged` converts nonzero exits, missing binaries, and timeouts; everything else raises it deliberately.
3. **Every external effect is an injected callable** (`run`, `which`, `popen`, `urlopen`, `sleep`, `call`, `kill`, `bind`). The test suite (416 tests, run in CI on Linux, macOS, and Windows) runs locally in under a second with no network, no Docker, and no real processes — and two autouse fixtures keep it that way: one points `LEPIKA_HOME` at a temp dir so tests can never touch a real `~/.lepika`, the other replaces `urllib.request.urlopen` with a function that raises a `BaseException` (`tests/conftest.py`, `RealNetworkCall`), so a probe left un-faked fails the test instead of being caught by the code's own `except Exception` and passing on `False`.
4. **Model refs, one field, three shapes:** `qwen3:8b` (Ollama tag) · `hf.co/<org>/<repo>` (Ollama pulls a GGUF build from Hugging Face) · `<org>/<repo>` (full weights: imported into Ollama by `engine.import_model` in Express mode on Apple Silicon — NVIDIA on Linux/Windows arrives with the MLX bundle installer — served by vLLM in Server mode on Linux + NVIDIA; refused with a GGUF hint anywhere else). The format is never guessed from the name: Ollama's "not GGUF" refusal (`engine.NotGGUF`) falls through to an import, and the pre-flight file list (`hf.preflight`) sends a GGUF-only repo to a pull.
5. **The curated list is data, not code.** `models.toml` ships in the wheel and is re-fetched from `main` at runtime (3s timeout). Remote content is untrusted: unknown keys are dropped, bad types and missing fields skip the entry, parse errors fall back to the bundled copy. The bundled copy parses strictly so defects fail in CI.
6. **Health-check first, act second.** A healthy `lepika up` makes zero subprocess calls and works offline. Restarts wait for the old server to actually die before declaring victory. Server mode is the one exception (rule 8): `docker compose up -d` is itself the reconciler — idempotent, about a second when nothing changed, and the only thing that makes a `connect` or `expose` edit take effect.
7. **pid files are hints, not truth.** A pid is only signalled if the webui is actually answering on the configured port — a stale file after a reboot can never kill an unrelated process. `ollama.pid` needs a third check (`ps` / `tasklist` must name an `ollama` binary), because `lepika down` leaves the engine running on purpose: that pid file routinely survives a reboot, and the OS's own Ollama service answering on 11434 would otherwise vouch for a recycled number. Stopping is then waited out, not assumed (rule 6) — a signalled Ollama unloads its models before the port comes free, and the pid file is kept if it never does.
8. **Two backends, one surface.** `express` and `server` both implement `start_stack(info, cfg, after_engine)`, `stop`, `update`, `logs`; `cli._backend(cfg)` picks one from `config.mode`, so every lifecycle command is written once instead of branching. Server's `start_stack` always runs `docker compose up -d --remove-orphans` and explicitly stops the services whose profile just went inactive (one `compose stop` naming all of them), because compose will not. It also asks `docker compose ps -q ollama` before refusing a busy port 11434: the stack publishes exactly `127.0.0.1:11434`, so from the second `lepika up` onwards the engine holding that port is our own container. Changing mode stops the backend being left first (`wizard.leave_mode`): both serve the UI on the same port, so an abandoned stack doesn't just linger — it answers. Leaving Express also stops the native Ollama LePika itself started (`express.stop_ollama`, keyed on the pid file `start_ollama` writes), because the Server stack needs port 11434 back; an engine the machine already ran has no pid file and is left alone, exactly as `lepika down` leaves every Ollama alone. And the new mode is only saved once the engine is up — a pre-flight that refuses must not leave a config claiming a mode that never started.
9. **The engine is managed or remote, never guessed.** `config.engine_managed` decides whether LePika installs and starts an engine. `lepika connect` clears it, `--local` sets it again; a remote engine may only be checked for an answer — never installed, started, or stopped.
10. **The model picks the engine.** An `org/repo` ref means vLLM in Server mode — `server.vllm_allowed` is Server mode + Linux + NVIDIA + a managed engine; everything else means Ollama. In Express mode an `org/repo` ref means an Ollama import — `express.import_allowed` is Express + a managed engine + Apple Silicon (NVIDIA on amd64 joins it with the MLX bundle installer); `cli._acquire` is the one place that decides pull vs import for both `model add` and the wizard, and returns the name the engine now serves, which is what the config stores. `server.vllm_active(cfg)` (Server mode + a managed engine + a repo ref) is the single predicate every caller shares, so there is no separate "engine" setting to keep in sync. It reads the mode as well as the model, so an Express config still naming a repo — a switch that failed halfway — does not make `status`, `doctor`, or `model list` report a vLLM that cannot exist there. Switching models starts the stack for the *target* ref (`dataclasses.replace(cfg, model=…)`), because the profile follows the ref and the config is only saved once the pull or import succeeds.
11. **Secrets are boring.** The API key is `secrets.token_urlsafe(32)`. `config.toml` and `stack/.env` are created 0600 with `os.open` plus an `fchmod`, which is what tightens a stale world-readable temp file that `O_TRUNC` would otherwise reuse — private from the first byte, not chmod'ed once the secret is already on disk. Secrets reach containers through `.env`, never argv, and are redacted from the log by key name. LePika owns `compose.yml`; `.env` is yours — the keys LePika manages are rewritten, everything else (image pins, `HF_TOKEN`) is preserved. Values are single-quoted so JSON and `$` stay literal; a value containing a `'` (a key from `lepika connect --key`) is written double-quoted with `\` and `"` escaped, which is the other form compose's .env parser accepts.
12. **Logs are for reading.** One JSON line per action or failure, events named `area.action`. A pure read writes nothing (`run_logged(..., log=False)`), health probes write nothing, and a command's output is recorded only when it failed — the last 40 lines, not a dump. Keys that name a credential (`key`, `api_key`, `token`, `hf_token`, `engine_key`, `password`) are masked before the line is rendered, because the log is what users are asked to paste into an issue.

## Notes for maintainers

- **PyPI:** LePika is not published to PyPI yet. Installers therefore install from this repository (`git+https://…`) and must never install a bare name we don't own. Publishing requires registering the distribution name first.
- **Ports:** conflict detection probes both `0.0.0.0` and `127.0.0.1` (macOS lets loopback bind over a wildcard listener) and uses `SO_EXCLUSIVEADDRUSE` on Windows.
- **What listens where (Express mode):** OpenWebUI is started with `--host 127.0.0.1` — it binds `0.0.0.0` by default — and native Ollama is already loopback-only, so Express reaches the network at no point. `lepika expose` is Server-only, which makes "nothing listens beyond localhost until you expose it" true in both modes.
- **What listens where (Server mode):** OpenWebUI is published on `WEBUI_BIND:webui_port` — `127.0.0.1` until `lepika expose` flips it to `0.0.0.0`. The ollama container is pinned to `127.0.0.1:11434` and vLLM to `127.0.0.1:8000`, so the engine is never reachable except through Caddy on `api_port` (11435), and only with the `expose` profile active; once exposed, the chat UI is the other LAN-facing port, protected by its own sign-in.
- **Imports ride Ollama's experimental surface.** `ollama create --experimental -q nvfp4` is undocumented in `ollama create --help` beyond the flag; the floor is 0.32.0 (the x/create rewrite that fixed nvfp4 corruption on Qwen3.5). Pre-quantized `mlx-community/*` repos do not import (Ollama reads them as bf16 and the runner panics) — only raw bf16 plus Ollama's own `-q`. Before a release, re-run `lepika model add Qwen/Qwen3.5-2B` on the Mac; if `--experimental` disappears upstream, `engine.import_model` is the one line to change.
- **`ollama` and `open-webui` track latest** by design; `lepika update` is the refresh path. CI never pulls a model or a container image (the unit suite is network-free, rule 3), so upstream breakage is not caught automatically: before a release, run `lepika update` and the wizard on a real machine in both modes.
- **`models.toml` is checked, not scraped.** Before a release, confirm every ref still resolves on the registry (the OCI manifest endpoint Ollama itself pulls from): `grep '^ref' models.toml | sed 's/ref = "//;s/"//' | while read r; do echo "$(curl -s -o /dev/null -w '%{http_code}' "https://registry.ollama.ai/v2/library/${r%%:*}/manifests/${r##*:}") $r"; done` — every line should start with `200`. The loop understands `name:tag` refs only — an `hf.co/…` or `org/repo` entry, should one ever ship, is checked by hand (`ollama pull` / the Hugging Face page).
- **OpenWebUI persists its own config:** the first run stores the engine URL from its admin panel and ignores the environment afterwards, so LePika starts it with `ENABLE_PERSISTENT_CONFIG=false` in both modes (and `OLLAMA_API_CONFIGS` when the engine needs a key) — otherwise `lepika connect` would move the engine everywhere except in the UI. `lepika connect` is the way to change the engine; the admin panel is not. The environment is read once, at startup, so `connect` also restarts a UI that is already up: `lepika up` alone would leave the healthy old process pointed at the old engine.
- **OpenWebUI's data and interpreter (Express mode):** LePika sets `DATA_DIR` to `~/.lepika/openwebui/` (chats, users, uploads, which otherwise live inside the uv tool venv that `lepika update` rewrites) and `WEBUI_SECRET_KEY` to a `secrets.token_urlsafe(32)` kept in a 0600 `openwebui/secret_key` (unset, OpenWebUI drops a `.webui_secret_key` into the caller's working directory), and pins `--python 3.11` on all three `uv tool` calls (`install`, `upgrade`, `run`) — the run must name the same interpreter as the env it is meant to reuse, or uv builds an ephemeral environment on the system Python instead.
- **Known trade-off:** `lepika down` treats a hung-but-alive webui as stale (won't signal it). Follow-up idea: pid liveness fallback.
- **Server mode owns its files.** `server.py` copies `compose.yml`, `compose.nvidia.yml`, and `Caddyfile` out of the wheel into `~/.lepika/stack` on every run, overwriting them — they are LePika's, and local edits are lost. `.env` is the merge-preserving exception (rule 11), which is what keeps a pinned `OLLAMA_IMAGE` across a `lepika update`. The GPU overlay is a second `-f` file rather than a condition inside `compose.yml`, added only when Docker can actually hand the GPU to a container (`nvidia_in_docker`).
- **Exposure is opt-in and always keyed.** `lepika expose` writes the key into `.env` *before* starting the stack, then re-runs `start_stack` so the `expose` profile (Caddy) and `WEBUI_BIND=0.0.0.0` apply. `start_stack` refuses the `expose` profile with an empty key: Caddy matches `Bearer {$LEPIKA_API_KEY}`, and an empty key makes a bare `Bearer ` header an open proxy. The key is printed to the terminal only.
- **`lepika expose` is Server-only** because the Bearer check is a Caddy container. An Express-mode user who wants to share an engine can run `OLLAMA_HOST=0.0.0.0 ollama serve` themselves — deliberately not wrapped, because an unauthenticated engine on the network is not something LePika should make one command away. The mirror image is `lepika connect`, which probes Ollama's `/api/version`: a box serving a full-weight repo on vLLM has no Ollama, so `expose` there prints the OpenAI-compatible `/v1` URL to add in OpenWebUI instead of a `connect` line.
- **Output is UTF-8 on every platform.** `cli.run` reconfigures `sys.stdout`/`sys.stderr` to UTF-8 before anything prints: Windows hands a piped or redirected stdout the ANSI code page, which cannot encode `✓`/`✗`, and the resulting `UnicodeEncodeError` would be a traceback (rule 2) on every status line. Found by running Express on a Windows runner.
